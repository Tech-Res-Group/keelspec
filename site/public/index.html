Governance for coding agents

The gate for software factories.

Bring any agent fleet: Claude Code, Codex, Devin, Copilot. KeelSpec decides what merges. Its gate calls no model and belongs to no agent vendor, so it can check all of them. Devin can't credibly check Devin, and Factory can't check Factory.

How it works

Spec. Any agent. Gate.

KeelSpec owns the three things a builder should not own about its own work: the intent it is judged against, the check that judges it, and the record of what passed.

  1. 01
    The spec

    Typed product intent, in your repo.

    Features, rules, decisions, whatever types you declare: markdown with typed frontmatter, validated as a graph and compiled into a committed bundle. Open questions stop the line before design, and named roles accept the spec.

    PAC-060 fails the build when the committed bundle drifts from its sources.

  2. 02
    Any agent

    The builder is swappable.

    Every station runs through one Runner seam. The library ships runners for the Anthropic API and for any OpenAI-compatible endpoint, such as your own model gateway, and you can supply your own. A pull request from any agent, or any person, meets the same gate.

    Roadmap Ready-made adapters for Claude Code, Codex, Devin and Copilot's coding agent.

  3. 03
    The gate

    Deterministic first, then a person.

    keelspec validate calls no model. The same tree gets the same PAC-NNN verdict on every pull request, and the exit code is the contract. Inside the line, five critics try to refute each change, with an optional sixth on a different model provider.

    Nothing auto-merges. A human does.

The method

KeelSpec runs the FastPDLC lifecycle.

Ten stations from a written-down story to production. KeelSpec automates the engineering segment, from understanding the spec to a change that has been built, tested and attacked. Everything after the pull request is a hand-off to the process you already run.

ST-06 · Verify

Five agent critics, each trying to refute the work.

The agent that builds a change does not get to grade it. A separate station attacks the result through five independent lenses, each defaulting to refuted unless convinced. Four ask whether the change meets its specification; the fifth asks whether the business process around it survives.

correctness

Find an input where it does the WRONG thing — and do the tests pass vacuously?

agent critic

coverage

Does every acceptance criterion map to a test that would catch its regression?

agent critic

security

Payments lens: authz, trust boundaries, injection, PII, secrets, spend / consent.

agent critic

reproduce

Ignore the happy path: concurrency, partial failure, retries / idempotency, rollback.

agent critic

integrity

Every criterion passes — so which business scenario, exception path or downstream consumer does it still break?

agent critic
Optional sixth

--cross-provider adds a verdict from a model outside the builder's family, so it cannot share the builder's blind spots. It sees a diff summary and test notes, without product context. If the call fails, it abstains rather than blocking.

Evidence

The audit trail an SDLC or model-risk review asks for.

The review starts with “prove your documented rules matched what you shipped.” KeelSpec answers with files in your repository, checked by recomputing digests rather than by trusting whoever produced them.

  • # keelspec evidenceA content-addressed record: the commit, whether the tree was clean, the tool version, the config, a SHA-256 for every artifact and the bundle, every finding, and the result. Its exit code follows validate, so CI gates and records in one step.
  • ✓ --verifyRecomputes every digest against the tree. For an old record, check out its commit and run it again: bundles are byte-stable.
  • ✎ Run records and named approvalsEvery orchestrated run keeps each station's output, every verdict, the triage cause and the risk tier. Required approvers sign the spec by role, and the commit that fills in the name is the signature.

KeelSpec produces evidence. It does not make you compliant and holds no certification. What the evidence must show is your organisation's policy.

Where it fits

On top of your agents, not instead of them.

Devin, Factory.ai, Claude Code, Codex and Copilot's coding agent build software. KeelSpec does not compete with them on building. It is the part a builder cannot credibly supply for itself: a check it does not control.

Your agent fleet brings

  • The builder, and whatever runs it: sandboxes, parallel runs, IDE and chat integrations, ticket intake.
  • Its own review and testing, if you use them.
  • Its own pricing, hosting and enterprise terms.

KeelSpec adds

  • Typed, versioned intent the change is judged against, with PAC-060 on drift.
  • A gate that calls no model and belongs to no agent vendor or model provider.
  • Five refuting critics, an optional sixth on a different model provider, and triage before repair.
  • Evidence records that are verified by recomputation.
  • All of it in your repo and your CI: pip install keelspec, a GitHub Action, Apache-2.0.

KeelSpec does not

  • Run agents in managed sandboxes or in the cloud.
  • Replace your CI, CD or change management. ST-07 to ST-10 are hand-offs.
  • Provide SSO, or hold SOC 2 or any other certification.
  • Merge anything.

The spec, in practice

Declare it. Author it. Gate it.

One config file, plain markdown artifacts, and a command whose exit code is the whole contract.

01

Declare your types

There is no fixed schema. You name the collections, the required fields, the id prefixes, the allowed values, and which fields must resolve to other artifacts.

# product.config.yaml
product_dir: product
output: build/product.generated.json
types:
  - name: terms
    dir: terms
    id_prefix: "TERM-"
    required: [id, term, definition]
    fields: [term, definition, see_also]
    references:
      - field: see_also
        to: terms
02

Author the artifacts

Markdown with YAML frontmatter, one file per artifact, in your repo, reviewed in pull requests like everything else. The prose below the fence is yours.

<!-- product/terms/TERM-payment.md -->
---
id: TERM-payment
term: Payment
definition: An instruction to move
  money between two parties.
see_also: [TERM-ledger]
---
The canonical unit of work in
the system.
03

Gate the build

Compile the bundle, commit it, and let CI (continuous integration) prove it still matches the source. Non-zero exit means the pull request does not merge.

# .github/workflows/product.yml
jobs:
  validate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: Tech-Res-Group/keelspec@v1.0.1
        with:
          config: product.config.yaml
          plugin: product_hooks.py
The enforcers

Seven codes stand between you and drift.

These run on every pull request, including one an agent opened. Every finding carries a stable PAC (product-as-code) PAC-NNN code. Codes are an API — continuous integration (CI), dashboards and humans match on the code, never the prose. Existing codes are never renumbered.

PAC-001

Required field

An artifact is missing a field its type declares as required.

missing required field 'definition' Schema
PAC-010

Id prefix

An id does not start with the id_prefix its type requires.

id 'payment' must start with 'TERM-' Identity
PAC-011

Filename match

The id and the filename disagree, so the artifact can't be found by either.

id 'TERM-payment' must match its filename Identity
PAC-012

Duplicate id

Two artifacts in one collection claim the same id. References become ambiguous.

duplicate id 'BR-idempotent' in type 'rules' Identity
PAC-020

Dangling reference

A reference field points at an artifact that does not exist. This is the one that catches renames and deletions before a reviewer ever opens the PR.

see_also 'TERM-leger' does not resolve to a terms id Graph
PAC-030

Enum violation

A field value is outside the allowed set its type declares.

status 'in-progres' not in ['done', 'in-progress'] Schema
PAC-060

Staleness — the one nobody else has

The committed bundle no longer matches the artifacts that produced it. Somebody edited the source and didn't rebuild, or edited the build and didn't touch the source. Either way, what you ship and what you wrote have parted company — and CI says so, in the diff, on the pull request.

build/product.generated.json is stale
— run: keelspec build (and commit it)

Plugin outputs are staleness-gated too, so a generated catalogue or a runtime manifest can never quietly fall behind.

A day in the life

Life of a pull request.

Someone renames one term. Here is what happens with KeelSpec in the loop — and what would have happened without it.

09:14

A rename lands.

An engineer decides TERM-payment was always the wrong word and renames it to TERM-charge in a pull request. One file changed. Looks harmless.

09:14

CI goes red before a human looks.

Three artifacts referenced the old id — two terms and a business rule. The graph no longer resolves, so the gate fails with the file and field named.

PAC-020 ×3
09:22

The graph gets fixed, not the prose.

Three see_also values updated, keelspec build run once. The bundle regenerates deterministically — sorted keys, byte-stable output, so the diff is exactly the change and nothing else.

09:23

Staleness clears.

The committed product.generated.json matches its sources again. Green. The reviewer now reviews a decision, not a consistency puzzle.

PAC-060 resolved
09:31

Merged — and everything downstream already knows.

The docs site, the in-app glossary, the internal catalogue and the context you hand an LLM all render from the same bundle. Nobody wrote a migration doc. Nobody had to remember.

Without the gate

The rename merges. Three documents keep pointing at a term that no longer exists. Nobody notices for eleven months, and by then two of them have been copied into a slide deck.

Plugins

Your checks. Your codes. No fork.

Real projects need more than schema. A plugin registers project-specific validators, enriches the bundle, and emits extra generated outputs — which is how a large codebase migrates onto KeelSpec with no loss of functionality.

  • fn ValidatorsCross-file checks the config can't express — does this links.code path actually exist on disk?
  • ⇄ Bundle transformersDerived fields computed at build time: reverse edges, rollups, denormalised views your renderer wants.
  • ⤓ Extra outputsEmit a runtime catalogue or manifest alongside the bundle — and it is staleness-gated exactly like the bundle is.
  • 9xx Your own diagnostic codesRegister codes in a project range so they never collide with the core set. Your CI matches on them the same way. 
# product_hooks.py
from keelspec import register

def register(reg):
    register("PAC-900", "links.code path does not exist")

    @reg.validator
    def code_paths_exist(bundle, config, root, report):
        for f in bundle["features"]:
            for path in f.get("code") or []:
                if not (root / path).exists():
                    report.add("PAC-900",
                               f"missing {path}",
                               f["_file"])

    @reg.bundle_transformer
    def reverse_edges(bundle, config, root):
        ...  # enrich the bundle in place

    reg.extra_output("build/catalogue.json", render)

Questions

The obvious objections.

How is this different from Confluence, Notion, or a docs site?
Those store prose and trust people to keep it honest. KeelSpec stores typed artifacts with a declared schema and a reference graph, and it runs in CI. Nothing merges while the graph is broken. It's a compiler, not a wiki — and you can keep your wiki, rendering it from the bundle.
Does it replace my documentation site?
No. It produces product.generated.json. Your docs site, your app's in-product glossary, your internal catalogue and the context you feed an LLM all render from that one bundle — so they can't disagree with each other.
My artifacts don't look like your glossary and rules.
There is no built-in schema. You declare your own collections, required fields, id prefixes, allowed values and reference edges in product.config.yaml. Terms and business rules are just what the quickstart happens to use. Decisions, features, personas, risks, invariants, migrations — all the same mechanism.
What if I need a check the config can't express?
Write a plugin. Register validators, bundle transformers and extra generated outputs, plus your own diagnostic codes in a project range like 9xx so they never collide with the core set. No fork, no patched engine — this is how a large existing project migrates without losing any of its bespoke checks.
Does this only work in Python repositories?
The CLI is Python — pip install keelspec, or use the GitHub Action which installs it for you. What it validates is plain markdown with YAML frontmatter, so the repository itself can be Go, TypeScript, Rust, Java or anything else. Nothing about your build system has to change.
Why commit the generated bundle? Isn't that a build artifact?
Because that's what makes PAC-060 possible. If the bundle only exists inside CI, nothing can prove that what you ship matches what you wrote. Committing it turns invisible drift into a visible diff on a pull request — and makes the build deterministic and reviewable.
Which coding agents does it work with?
The gate works with all of them, because it reads the repository, not the agent: keelspec validate runs in your CI on every pull request, whoever opened it. The built-in line, keelspec orchestrate, runs its stations through a Runner; the library ships runners for the Anthropic API and for any OpenAI-compatible endpoint, and you can write your own. Ready-made adapters for Claude Code, Codex, Devin and Copilot's coding agent are on the roadmap, not built yet.
Does KeelSpec make us compliant?
No, and it does not claim to. It holds no certification and provides no SSO or access control; those come from your Git host, your CI and your organisation. What it gives an SDLC or model-risk review is evidence: content-addressed records you can verify by recomputing digests, run records, and named approvals by role.
What is FastPDLC?
The name of the method: ten stations from a written-down story to production, ST-01 to ST-10. KeelSpec automates ST-01 to ST-06 and treats ST-07 to ST-10 as hand-offs to your own process. Versions up to 0.6.3 of the tool itself were published as fastpdlc; the package is now keelspec.
What licence is it under?
Apache-2.0. Use it, embed it, ship it; there are no obligations back beyond the notice. Your product artifacts and your plugins are yours. Versions up to 0.6.3 were LGPL-3.0-or-later.
